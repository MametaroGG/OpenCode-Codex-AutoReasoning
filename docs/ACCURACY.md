# 実モデル精度検証の方法

Gemma判定役の追加調査は [Gemma接続検証](GEMMA-EVALUATION.md) を参照。初回生成がHTTP 502で失敗しており、精度は未評価。

この文書は初回Luna精度評価時の記録。現在の製品の判定役は**Luna専用**。Haikuの選択機能は試作後に撤去し、実精度は未測定。ここにあるローカル・hybridの比較は履歴であって選択可能な機能ではない。旧ローカル実装は比較再現用の `scripts/baselines/` に隔離した。現行の既定タイムアウトは15秒だが、以下の「3秒」は評価当時の既定値を指す。判定プロンプト・JSON検証は変更していない。別途 [実ホスト試験](LIVE-HOST-VALIDATION.md)でLuna判定を2回追加実行したが、以下の48回の精度集計には混ぜていない。

## 対象と事前固定

- 対象は `openai/gpt-6-luna#low`。開発用モデルの切替や実装作業は行わない。
- ユーザー承認は合成課題24件×2回、最大48回の独立した生成API呼び出し。
- `tests/fixtures/accuracy-v1.json` に各難易度6件ずつの日本語・英語の課題を事前に固定。課題、前のuser指示、ファイル数だけを送信し、期待ラベル・評価用理由・実プロジェクト・実際の会話は送信しない。
- 過去の開発用ベンチマークとは別の課題を使用する。ラベルは開発者が付けたものであり、第三者専門家の合意や客観的な正解を保証しない。
- 評価中は判定プロンプト・判定ロジック・ラベルを調整しない。調整後の再評価は別セット・別承認で行う。

## 実行経路

`scripts/evaluate-live.ts` が実装本体の `createModelClassifier` と出力検証器を使用する。生成の接続部分だけを、公式の `opencode api post /api/experimental/generate/text` へのCLIブリッジで置き換える。モデル応答はモックではない。

OpenCodeがサーバーの発見・認証を行い、本スクリプトは認証情報を解決・取得・保存しない。CLIへのリクエスト本文は標準入力を使い、シェル文字列へ挿入しない。モデル、variantは固定であり、自動フォールバックや手動の再試行は行わない。SDK・プロバイダ内部の自動リトライ有無までは計測しない。

1回目の24課題を実行後、同じ順序でもう一度実行する。隣接した同一課題だけで安定性を評価しない。キャッシュは使わず、48回とも実モデルで判定する。hybridの結果は、同じ応答と既存のローカル早期判定規則からオフラインで算出し、追加のモデル呼び出しは行わない。

各呼び出し前に `evaluation-results/accuracy-v1/ledger.jsonl` へ開始を記録する。既存の台帳は上書きせず、誤って同じ承認で再実行することを防ぐ。途中失敗も承認回数を消費するものとして扱い、自動再試行せず停止する。台帳・最終レポートには課題と判定結果、時間、ハッシュを残す。プロバイダの例外本文は保存しない。

## 指標

- **完全一致率**: 期待する4段階の難易度との一致。不正応答・失敗も分母に含める。
- **有効応答のみの一致率**: 失敗を分けて理解するための補助指標。
- **過小・過大評価**: 段階順で比較し、2段階以上の過小評価を別に数える。
- **難しい課題の過小評価率**: 期待High/Very Highの課題に対する低い判定の割合。
- **再現一致率**: 同じ課題の2回の有効回答が一致した割合。誤答が安定しているだけの場合もあるため精度とは分ける。
- **混同行列**: 期待ラベルと実判定の組み合わせ。
- **応答時間**: 平均・中央値・95パーセンタイル・3秒超の件数。

CLI起動とAPI通信を含むため、応答時間はプラグイン内から直接呼ぶ場合の時間とは一致しない。評価では応答を最大60秒待ち、既定の3秒制限に収まりそうかを補助的に見る。60秒超は停止し、サーバー側で推論が継続する可能性を考慮して再試行しない。

## 検証できないこと

- 難易度の一致率だけでは、生成されるコードの品質や最適な思考量を証明できない。
- 24課題×2回は24個の独立課題であり、独立した48課題として一般化しない。
- 実際の会話・ソース構造を使わないため、現実のコードベースの難易度判断とは異なる。
- このAPIは使用トークン数・請求額を返さない。使用量と費用は不明とし、0と表記しない。
- これは実モデルの判定経路の検証であり、稼働中プラグインのprompt hook、ID対応、TUI表示を含む統合検証ではない。

## 実行

```powershell
# 必ず別途、外部送信と費用/利用枠の消費について承認を得てから実行する。
npm run evaluate:live -- --allow-live
```

`npm test` や `npm run benchmark` から実モデル検証は起動しない。実行結果は `evaluation-results/accuracy-v1/report.json` に記録する。

## 初回実測結果

記録時刻（UTC）: 2026-11-08T22:21:07.474Z。24種類×2回、承認された48回をすべて完了。失敗・不正JSON・手動再試行は0。稼働中プラグインの設定とグローバル設定は変更していない。

カタログ上の指定IDとAPIモデルIDはどちらも `gpt-6-luna`、providerは `openai` であることを確認した。別名モデルを選択したものではない。ただし生成APIの戻り値にはモデル識別情報や使用量が含まれない。

| 指標 | ローカル | GPT-6 Luna low | hybrid（同じ応答からのシミュレーション） |
|---|---:|---:|---:|
| 期待ラベルとの完全一致 | 14/48（29.2%） | 44/48（91.7%） | 44/48（91.7%） |
| 過小評価 | 24/48 | 4/48 | 4/48 |
| 2段階以上の過小評価 | 10/48 | 0/48 | 0/48 |
| 期待High/Very Highの過小評価 | 24/24 | 0/24 | 0/24 |
| 同じ課題の2回の判定一致 | 24/24 | 22/24（91.7%） | 22/24（91.7%） |

ローカル判定は決定的なので再現一致率100%でも正確とは限らない。既存の開発用ベンチマークの高い一致率が、新しい言い回しに一般化しないことを確認した。Lunaについても24種類の小規模セットであり、一般的な精度の保証ではない。難しい課題の24回答は12種類×2回で、24種類の独立した課題ではない。

### Lunaの混同行列

行が期待ラベル、列が実判定。各行は6課題×2回。

| 期待＼実判定 | Very Low | Low | High | Very High |
|---|---:|---:|---:|---:|
| Very Low | 12 | 0 | 0 | 0 |
| Low | 4 | 8 | 0 | 0 |
| High | 0 | 0 | 12 | 0 |
| Very High | 0 | 0 | 0 | 12 |

差異はすべてLow（要求effort=medium）をVery Low（low）とする1段階の過小評価だった。

- `lo-01`: 単一コンポーネントの空状態表示。1回目Low、2回目Very Low。
- `lo-03`: 省略可能な設定値のデフォルト追加。1回目Low、2回目Very Low。
- `lo-06`: 既存booleanによる送信ボタンの無効化。2回ともVery Low。

これらは小機能と極小変更の境界であり、期待ラベル自体にも判断の余地がある。ただし結果に合わせてラベルを変更したり、誤りを一致として扱ったりしていない。難易度ラベルの差を、そのまま実装品質の低下と同一視もしない。

### 待ち時間と費用

- 平均: **3.64秒**、中央値: **2.92秒**、95パーセンタイル: **7.81秒**。
- 最大: 約12.39秒。
- **22/48回が3秒超**。評価では60秒まで待っており、これを本番のタイムアウト失敗率とは呼ばない。CLI起動・通信のオーバーヘッドを含み、直接呼ぶプラグイン経路とは異なるためである。
- 既定のモデル判定タイムアウト3秒は短い可能性がある。5〜10秒以上の許容時間、待ち時間を減らす運用、キャッシュの有効性を検討すべき。今回の依頼では既定値を変更していない。
- 使用トークン数・実請求額はAPIから返されず**不明**。API課金か契約枠消費かもこの結果だけで断定しない。48回の追加生成API呼び出しは記録済みで、追加の再評価は実施していない。
- hybridでローカル即決になったのは24課題中2課題。このセットなら2回分で4回のモデル呼び出しを省略できる計算だが、実際の評価では比較のため48回すべてLunaへ送った。

### 判断

**このセットでは、Lunaを判定役に使う方がローカル判定のみより有望。** 特に未知の言い回しや専門課題の過小評価を減らした。ただし、無料モデル・Terra等との比較はしていないため、最もコスパがよいモデルだとは断定できない。開発成果物のテスト合格率とトークン節約の検証も別途必要である。
